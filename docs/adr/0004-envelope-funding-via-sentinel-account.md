# Envelope funding is a Transaction against a sentinel Account

> **Note:** the "no dedicated funding endpoint" consequence below was reversed by [ADR 0006](0006-dedicated-fundings-endpoint.md), which adds `POST`/`GET /fundings` as a thin wrapper over the same mechanism. The model described here — funding as an ordinary Transaction against the sentinel Account — is unchanged.

v2 needed a way to earmark money already sitting in an Own Account for a purpose ("Groceries", "Vacation") without physically moving it anywhere — the earmark is virtual, the money doesn't leave. The chosen mechanism: a reserved External Account with a fixed id (`0`, name "Envelope"), seeded once at migration time before any user-created Account can claim that id. "Funding" an Envelope is then an ordinary Transaction — `account_id` = the real Own Account, `opposing_account_id` = `0`, `envelope_id` = the Envelope being funded. A generated column, `is_funding` (`opposing_account_id = 0`), flags these rows.

This was chosen over two alternatives considered and rejected:

- **A real sub-account per envelope** (actually moving money into it) — rejected because it contradicts the premise: an Envelope holds no currency of its own, it's a label over money that's still sitting in a real Account. Modeling it as a place money moves to would mean every allocation needs a matching real transfer to reconcile, for a mechanism whose entire point is to avoid that.
- **A separate reservation table outside the Transaction model** — rejected because this API's whole surface is already "everything is a Transaction" (Transfers, spends, and now envelope funding all go through the same `POST /transactions`/`POST /transactions/batch`, with no per-scenario endpoint anywhere — see `docs/spec-v1.md`). A parallel non-Transaction concept would be the only exception to that uniformity.

`envelope_id` is a plain nullable column on `transactions`, not restricted to funding rows — it's deliberately also legal on a Transfer between two Own Accounts, which lets a reservation follow real money moved from the Account it was funded in to the Account it's actually going to be spent from (verified end-to-end in [wayfinder ticket "Define piggy banks for v2"](https://github.com/bmblb3/pennywise/issues/26): fund in Savings, spend on a Credit Card, transfer the reservation to Checking, pay off the card — every step tagged the same Envelope, and the numbers reconcile to zero once the card is paid).

Since a funding Transaction is a real row with a real `account_id`, it would otherwise distort that Account's reported balance under v2's existing `GET /balances` definition (closed in [Spec: GET /balances](https://github.com/bmblb3/pennywise/issues/24), which sums `GET /postings`). `GET /postings` is renamed to `GET /ledger`, backed by a view that excludes `is_funding` rows — real balances and statements only ever see real money movement. `CONTEXT.md`'s **Ledger** definition narrows accordingly (was "the complete record of Transactions," now "the record of real-money Transactions"). Raw visibility into funding Transactions (e.g. for an audit trail) isn't lost — `GET /transactions` already lists every row verbatim, funding included.

The schema, views, and every scenario below are pinned as runnable assertions in [`0004-envelope-funding-via-sentinel-account.verify.sh`](0004-envelope-funding-via-sentinel-account.verify.sh) — a plain `sqlite3` script, no framework, run with no arguments. It exists so an eventual Rust implementation has a spec to build against and a regression net to refactor under, not because this ADR needed proving twice.

## Consequences

- An Envelope's balance is computed per `(account_id, envelope_id)`, never summed across Accounts — funding the same Envelope from Accounts of different Currencies is legal (e.g. a EUR, USD, and THB Account all funding one "Vacation" Envelope for a trip), and summing across Currencies would be meaningless anyway. A client wanting a combined total groups the per-Account rows itself, consistent with this API's existing no-server-side-aggregation stance.
- Funding an Envelope from an Account that doesn't have the money is legal — nothing here enforces non-negative balances. `account_headroom` (`bal - still_reserved`, `bal` from `GET /ledger`, `still_reserved` the sum of each Envelope's non-negative balance in that Account) is designed to surface exactly this as a negative "headroom," a signal rather than a rejected write.
- An overspent Envelope (spent more than funded) reports a negative balance in `envelope_balances`, but contributes `0` — never negative — to `still_reserved`: an Envelope can't reserve money it doesn't have, and the overspend already shows up as reduced real balance via `GET /ledger`.
- This is a breaking rename of a v1 endpoint (`GET /postings` → `GET /ledger`), carried out in v2 rather than left for v1 to decide, in the same category as the `batch_id` removal ([ADR 0003](0003-drop-batch-id.md)).
