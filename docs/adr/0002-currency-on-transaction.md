# Currency lives on the Transaction, not the Account

An Own Account has no intrinsic Currency; `accounts.currency_id` from the original schema draft was dropped, and `transactions` instead carries `currency_id` (required) and `opposing_currency_id` (nullable, meaning "same as `currency_id`"). This was decided because real accounts the ledger owner holds — cash, Wise — genuinely hold balances in more than one currency at once. Pinning a single Currency to an Own Account made those accounts unrepresentable without splitting each into artificial per-currency rows (`Wise (SEK)`, `Wise (USD)`), which isn't what they actually are. It also lets FX detail be recorded on a purchase from an External Account (paid in USD, a foreign shop received JPY) — the account-level model couldn't express this at all, since External Accounts never had a currency to compare against in the first place.

## Consequences

The schema no longer guarantees "this account only ever holds SEK" — nothing stops a mistyped `currency_id` on any individual Transaction; that invariant is gone, not moved. A useful side effect: the old cross-table currency-mismatch rule collapses into two plain SQLite `CHECK` constraints on `transactions` (`(opposing_amount IS NULL) = (opposing_currency_id IS NULL)`, and `opposing_currency_id IS NULL OR opposing_currency_id != currency_id`), so the shared validation function shrinks to a single rule (`account_id` must be `'own'`). Any future per-account balance work must group by `(account_id, currency_id)` rather than sum one column, since an account can now genuinely hold more than one Currency.
